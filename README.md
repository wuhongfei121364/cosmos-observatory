# 宇宙万物观测站 · Cosmos Observatory

> **所选题目：题目二 · 宇宙万物观测站**
> 界面地址：**http://127.0.0.1:18000**

一个在单机上运行的观测系统。它持续接收对象发生器推送的“宇宙对象”，逐批校验、去重后可靠落盘，再通过网页把这个**数量巨大、格式未知、还在不断变化**的世界整理成可浏览、可搜索、可视化的形式。

| 关注点 | 做到了什么 |
| --- | --- |
| 数据可信 | 返回 2xx 时数据已写入磁盘；重复投递自动去重；坏数据整批拦截；用发生器的运行记录逐项核对，全部通过 |
| 性能 | Mac Docker Desktop 上持续约 **8,200 对象/秒**，60 秒入库 49 万对象，无 4xx/5xx |
| 可靠 | 运行中 `kill -9` 再重启，已确认的数据一条不丢、没有半截批次 |
| 好用 | 总览一屏看懂“世界由什么构成、数据流入得怎样”，点进浏览页按分类、坐标系、关键字查找对象 |

---

## 1. 快速开始

前提：Mac 上已安装并启动 Docker Desktop。整个系统**只依赖 Python 标准库**，构建时不需要联网安装任何包。

```sh
# ① 载入发题包里的发生器镜像（只需一次）
docker load -i /path/to/宇宙万物观测站/flightgen-image.tar

# ② 构建并启动：观测站 + 发生器
docker compose --profile gen up -d --build

# ③ 打开界面
open http://127.0.0.1:18000

# ④ 启动一轮数据：参数依次为 test_id、每秒对象数、持续秒数、场景
scripts/start_run.sh run-001 2000 120 evolving

# ⑤ 这一轮结束后，用发生器的运行记录核对入库数据
scripts/fetch_receipt_and_verify.sh run-001
```

压测（速率填 `0` 表示让发生器尽力发送）：

```sh
scripts/start_run.sh stress-001 0 60 stress
scripts/fetch_receipt_and_verify.sh stress-001
```

### 端口

| 端口 | 用途 |
| --- | --- |
| `18000` | 观测站：网页界面、查询接口 `/api/*`、数据接收 `/ingest`（容器内为 8000，宿主机端口可用 `OBS_PORT` 修改） |
| `9001` | 发生器控制接口：`/start`、`/status`、`/rate`、`/stop`、`/receipt` |

在 compose 网络内，发生器直接投递到 `http://observatory:8000/ingest`。如果按《发生器操作说明》用 `docker run` 单独启动发生器，就改为投递到宿主机端口：

```sh
TARGET=http://host.docker.internal:18000/ingest scripts/start_run.sh run-002 2000 120
```

### 其他常用操作

```sh
# 只重建观测站（改了代码之后），不影响发生器；数据在 ./data，不会丢
docker compose up -d --build observatory

# 运行中调速、查看状态
curl -fsS http://127.0.0.1:9001/rate -H 'Content-Type: application/json' -d '{"objects_per_second":5000}'
curl -fsS http://127.0.0.1:9001/status

# 不用 Docker，直接本地运行（Python 3.8+）
cd app && DATA_DIR=../data PORT=18000 python3 server.py
```

## 2. 界面

界面分两页，顶部导航切换。

**总览**：一屏看完统计结果。
- **已入库对象**，以及入库批次、分类数、分类树修订次数、当前速率。
- **世界由什么构成**：按大类统计对象占比的色带和排行表，点击任一大类直接进入浏览页并按它筛选。最大的 7 个大类着色，其余合并为“其他”；同一大类在所有页面颜色一致。
- **数据流入**：本批次全程每秒入库对象数的曲线，带坐标轴，悬停可读数，并标出当前、峰值、流入时平均速率。
- **数据可信度**：多少批校验后入库、多少批重复投递被去重、多少批坏数据被整批拦截，可跳转查看原因。

**浏览**：左侧分类树，右侧四个页签。

| 页签 | 内容 |
| --- | --- |
| 对象 | 按名称或 ID 搜索（输入即搜），按坐标系筛选，分页加载；新数据到达时只提示、不打断阅读。点击对象，右侧滑出详情：基本信息、属性表、原始 JSON |
| 星图 | 按坐标系（银河、恒星系、地表）画出最近 8000 个对象的位置，按大类着色，随分类筛选；悬停看对象，点击看详情 |
| 字段结构 | 数据格式未预先给定，这里按当前分类抽样推断每个字段的出现比例、值类型、数值范围和常见取值，并标出类型漂移 |
| 变化记录 | 分类树的改名和迁移历史；被拦截批次的编号和原因 |

分类树会实时反映发生器的新增、改名、迁移，节点显示含子类的对象数，改过的节点标“已变更”。

键盘：`/` 搜索，`↑` `↓` 选择，`Enter` 打开，`Esc` 关闭。

## 3. 数据探索：发生器发了什么

数据格式没有预先提供。我直接运行发题包中的发生器，抓取真实流量并结合 `flightgen preview / inspect` 分析，结论如下。

**两类消息**，都 POST 到同一个地址，用 `kind` 区分：

| kind | 含义 | 关键字段 |
| --- | --- | --- |
| `types` | 分类树的一次修订 | `revision` 依次递增；`changes[]` 中的 `op` 为 `create` / `rename` / `move` |
| `objects` | 一批对象 | `batch_id`、所依赖的 `tree_revision`、`objects[]` |

**对象字段**：`id`、`sequence`、`type_id`、`name`、`timestamp_ms`、`position`、`attributes`。
- `position` 可能为空，或是三种坐标系之一：银河坐标（光年）、恒星系坐标、地表坐标（米）。
- `attributes` 因类型而异：恒星有光谱与质量，飞机有高度与载客，设备有电量与读数，文档有页数与引用。同一字段的类型还会漂移。

**发生器故意注入的三类问题**（来自镜像启动参数）：

| 问题 | 比例 | 正确处理 |
| --- | --- | --- |
| 重复投递：已确认的批次再发一次 | 2% | 去重，返回 200，不重复存储 |
| 不完整：如缺 `type_id` | 1% | 整批拒收，返回 400 |
| 非法：如 `attributes` 是数组 | 1% | 整批拒收，返回 400 |

运行记录（receipt）中的 `fault_rejected_bitmap` 记录了发生器看到哪些坏批次被拒收，说明正确做法是把它们挡在外面。另外，对象批次依赖的分类树修订必须先被确认。

## 4. 系统设计

```
               POST /ingest
  发生器 ───────────────────▶ 处理线程：解析 + 整批校验
                                  │  不合法            → 400，整批不写入
                                  │  依赖的分类树未到达  → 409，请发生器重试
                                  │  队列已满          → 503，请发生器重试
                                  ▼
                              有界队列
                                  ▼
                       单写线程：合并多批，一次提交
                       写入磁盘（fsync）后才回复 200
                                  ▼
                        SQLite（WAL 模式，单文件）
                                  ▲
  浏览器 ◀──── /api/* 查询 ───────┘  只读连接，读写互不阻塞
```

### 写入：返回 2xx 时数据一定已经落盘

1. **整批校验**：一批中任何一个对象不合法，整批返回 400、不写入任何内容，并记录原因。
2. **保证先后顺序**：对象批次依赖的分类树修订还没存下来时返回 409，让发生器稍后重发。
3. **合并提交（group commit）**：单写线程把队列中积压的多批合进一个事务，提交并强制写盘后，才逐个回复 200。压力越大，一次合并得越多，写盘次数不随请求数线性增长。
4. **幂等去重**：批次表以 `(test_id, batch_id)` 为主键，重复投递直接返回 200、不再写入；对象表以 `(test_id, id)` 为主键再兜一层。分类树修订按修订号去重，并检查是否跳号。
5. **背压**：队列满时返回 503，由发生器重试，内存不会无限增长。
6. **统计随写入更新**：各分类数量、各坐标系数量、每秒入库数与数据在同一事务中增量更新，界面查询不必扫全表。

### 查询

- 列表查询都走索引，按序号倒序做游标分页，不使用 `OFFSET`。
- 分类子树筛选：内存中维护分类树，展开成 `type_id IN (...)`。
- **分类树会改名、迁移**：对象只记 `type_id`，名称和层级在显示时用最新的分类树解释，改名或迁移后不需要改写任何对象。

### 主要接口

| 接口 | 说明 |
| --- | --- |
| `POST /ingest` | 接收发生器消息 |
| `GET /api/runs` | 各批次（test_id）的汇总 |
| `GET /api/overview` | 总览统计 |
| `GET /api/rate?whole=1` | 本批次全程的每秒入库数 |
| `GET /api/tree` | 分类树（含子类计数）和改名、迁移记录 |
| `GET /api/objects` | 对象列表：`type_id`、`q`、`frame_kind`、`before_seq`、`limit` |
| `GET /api/object?id=` | 单个对象详情 |
| `GET /api/attrs` | 字段结构推断 |
| `GET /api/map` | 星图坐标 |
| `GET /api/rejections` | 被拦截批次及原因 |

## 5. 实测结果

每一轮都用 `scripts/verify_receipt.py`，以**发生器的运行记录为准**核对 7 项：

1. 发生器已确认的批次全部入库；
2. 库中没有从未发送过的批次；
3. 坏批次从未入库；
4. 发生器侧看到全部坏批次被拒收；
5. 对象数等于已入库批次大小之和，没有半截批次；
6. 已确认对象数 ≤ 入库对象数 ≤ 已发送对象数（运行到期时被中断的在途请求可能已入库但未被确认，这是允许的）；
7. 分类树修订号与发生器确认的一致。

**验收环境：Mac 上的 Docker Desktop（Linux arm64 容器）**

| 测试 | 参数 | 结果 |
| --- | --- | --- |
| 端到端 | evolving，2,000 对象/秒，60 秒 | 717 批 / 71,700 个对象全部入库；17 批重复投递被去重；10/10 坏批次被拒收；分类树修订 36 = 36；0 个 4xx/5xx、0 重试；平均延迟 46 毫秒 |
| 极限吞吐 | stress，尽力发送，8 并发，每批 100，60 秒 | **约 8,200 对象/秒（约 17.8 MB/秒）**，入库 491,400 个对象；0 个 4xx/5xx、0 超时、0 重试；平均延迟 94 毫秒；100 批重复投递被去重，78/78 坏批次被拒收；7 项核对全部通过 |

**开发环境：Linux arm64 虚拟机，4 核，不经过 Docker**

| 测试 | 参数 | 结果 |
| --- | --- | --- |
| 极限吞吐 | stress，尽力发送，16 并发，每批 100，30 秒 | 约 12,300 对象/秒（约 28 MB/秒），入库 369,800 个对象；0 个 4xx/5xx；平均每次提交 22.6 毫秒；62/62 坏批次被拒收 |
| 崩溃恢复 | 运行到第 8 秒时 `kill -9` 服务，1 秒后重启 | 发生器遇到 23 次网络错误、20 次重试；**已确认的 380 批全部在库**，没有半截批次和重复；宕机期间 3 批耗尽重试，未确认也未入库 |
| 查询速度 | 库内约 45 万对象 | 总览 3 毫秒，分类树 2 毫秒，列表（含筛选、搜索）1–6 毫秒，详情 1 毫秒；星图 8000 点 65 毫秒；字段推断 124 毫秒 |

两个环境的吞吐差异来自并发数（8 对 16）和 Docker Desktop 的虚拟化开销。

## 6. 关键取舍

| 选择 | 原因 | 代价 |
| --- | --- | --- |
| Python 标准库 + SQLite | 120 分钟内可交付、易解释；零依赖，镜像构建不需要联网 | 吞吐受 Python JSON 解析和 GIL 限制，4 核没有用满 |
| 每次提交都强制写盘（`synchronous=FULL`） | 保证“2xx 即落盘”，掉电也不丢已确认数据 | 吞吐比 `NORMAL` 低；靠合并提交弥补 |
| 坏数据整批拒收 | 不会出现半批数据，与发生器的预期一致 | 同批中合法的对象也一起被拒，需要发生器重发 |
| 对象存原始 JSON + 关键列 | 未知格式和类型漂移都能完整保留，可按关键列查询 | 每个对象约 2.7 KB（含索引） |
| 统计随写入增量更新 | 总览和分类树查询是毫秒级 | 写入路径多几条 UPSERT |

## 7. 已知限制

- 名称搜索用 `LIKE '%关键字%'`：命中多时很快，极少命中时要扫描较多行。更大规模应加 FTS5 全文索引，会牺牲一部分写入吞吐。
- 吞吐上限受单进程 Python 限制。要再提升，可改为多进程接收加单写进程，或把接收层换成编译型语言。
- 星图是最近 N 个对象的 x / y 平面投影，没有做空间索引、全量聚合渲染和跨坐标系换算。
- 字段结构是对最近 500 个对象的抽样推断，不是全量结构。
- 没有做数据保留和归档：按每个对象约 2.7 KB 计算，20 GiB 约可容纳 700 万个对象，更大规模需要压缩原文或冷热分层。

## 8. 目录结构

```
cosmos-observatory/
├── app/
│   ├── server.py            HTTP 服务：/ingest 接收、/api/* 查询、网页
│   ├── store.py             SQLite 存储：合并提交、去重、增量统计、重启后恢复分类树
│   ├── validate.py          消息与对象的校验规则
│   └── static/index.html    单页前端（原生 JS + SVG / Canvas，无需构建）
├── scripts/
│   ├── start_run.sh                  启动一轮发生器
│   ├── fetch_receipt_and_verify.sh   下载运行记录并核对
│   └── verify_receipt.py             以运行记录为准的 7 项正确性核对
├── Dockerfile               基于 python:3.11-slim，无 pip 安装，带健康检查
├── docker-compose.yml       观测站（4 核 / 4 GiB，端口 18000）+ 发生器（1 核 / 256 MiB，profile: gen）
└── requirements.txt         空：只依赖 Python 3.8+ 标准库
```
